# Milestone 3 — Visits Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Moni books site visits itself. It finds free slots from the sales roster, assigns a sales person fairly, and confirms the visit to the customer. The sales person gets a WhatsApp alert and a push with the handover summary. Staff see and manage every visit on a Schedule page, and each sales user sees their own leads and visits. Admins are pushed when Moni hands off or fails.

**Architecture:**
- **Scheduling** (`api/src/scheduling/`):
  - A pure slot finder over data loaded from the roster and visits.
  - A visit lifecycle module that writes visits under a Postgres exclusion constraint, so a double booking is impossible even under a race.
- **Outbound** (`api/src/outbound/`):
  - WhatsApp messages to sales (and the reassignment notice to customers) go through a `scheduled_messages` outbox.
  - A visit change commits its alert rows in the same transaction. A 1-minute poller sends them as approved templates, and holds them while no template is configured.
- **Push** (`api/src/notify/`): Web Push to staff accounts. It is best effort and is called after the change commits.
- **Moni:**
  - Four visit tools replace Milestone 2's interim "hand visits to staff" rule.
  - The lead state now shows the active visit, and the reply check rejects a claimed booking or a sales name that no tool returned.

**Tech Stack:**
- Everything Milestone 2 uses
- `web-push ^3.6.7` (+ `@types/web-push`)
- `@fastify/rate-limit ^11`
- the `btree_gist` Postgres extension

## Global Constraints

Everything in Milestone 1 and Milestone 2's Global Constraints still holds: two packages, Node ≥24, ESM with `.js` imports, the `{data, error}` envelope, the bearer secret, WIB display, Bahasa Indonesia UI, test contacts never reaching Chakra, and the model settings `MONI_MODEL` / `MONI_EFFORT`. Don't rename them to `CLAUDE_*`, because Claude Code exports `CLAUDE_EFFORT` into the shell. In addition:

- **Time:**
  - WIB is UTC+7 and has no daylight saving time, so date and time arithmetic uses the fixed `+07:00` offset, as `routes/leads.ts` already does.
  - Weekdays are ISO, `1` Monday to `7` Sunday, the same keys as `projects.gallery_hours`.
  - Dates are `YYYY-MM-DD` and times are `HH:MM` (24-hour), both in WIB.
- **Slots:**
  - A slot is `[start, start + visit_minutes)`.
  - Starts fall on a 30-minute grid that begins at the gallery's opening time.
  - `find_visit_slots` returns at most **6** slots, and at most **3** per day.
  - A search covers at most **14** days.
- **Visit statuses:**
  - Active: `scheduled`, `confirmed`, `awaiting_confirmation`.
  - Inactive: `rescheduled`, `cancelled`, `visited`, `no_show`.
  - A lead has at most one active visit.
  - A reschedule marks the old row `rescheduled` and inserts a new row with `rescheduled_from`.
- **Test chat:**
  - Visits for `is_test` contacts are stored with `is_test = true`.
  - They never block a real slot, never enter the exclusion constraint, and never alert anyone.
- **WhatsApp to sales:**
  - Sent only as an approved template through `scheduled_messages`, never as free text.
  - Template parameters are one line: no newline, no tab, no run of 4+ spaces, at most 500 characters (Meta rejects others).
  - The template name is read from Settings at send time. Until it is set, rows stay `pending` and the dashboard warns.
- **Phone numbers:** stored as digits in international form without `+` (`62…`). `0812…` becomes `62812…`.
- **Push:** best effort. A push failure is logged and never fails a request, a turn or a booking.
- **Roles:**
  - Lead and visit routes require `X-Staff-Id`, and the API looks up that staff row's role. A role header is never trusted.
  - Admins see everything. A sales user sees leads whose `assigned_sales_id`, and visits whose `sales_agent_id`, is the sales agent linked to their account.
- **Model calls:** the only new one is the summary refresh (Task 12). It uses `MONI_MODEL` at effort `low` through the same `client.beta.messages.create` call shape:
  - Same parameters: `betas: ['server-side-fallback-2026-07-01']`, `fallbacks: 'default'`.
  - Structured output via `output_config.format`, because forced `tool_choice` is a 400 on Opus 5.5.
  - Never sent: `thinking`, `temperature` or a prefill.

## Review Focus

1. **Two customers confirm the last free sales person for the same slot at the same moment** → one visit is booked; the other request gets `SLOT_TAKEN`, and Moni offers other times. Nobody is double-booked. Test: Task 8, `concurrent bookings for the last free agent: one wins, one SLOT_TAKEN`.
2. **The customer says "Sabtu" and the model passes a Friday's date** → the prompt's KALENDER line names each of the next 14 dates with its weekday, and every slot label carries the weekday. Test: Task 9, `the time block lists the next 14 days with weekday names`; Task 4, `slot labels carry the weekday of the WIB date`.
3. **A search runs late at night or early in the morning, when the WIB date differs from the UTC date** → slots belong to the WIB day, and the notice period counts from the real now. Test: Task 4, `a WIB morning is on the WIB date, not the UTC date`.
4. **The handover summary holds line breaks or long customer text** → the template parameters are flattened and clipped, so Meta accepts the alert. Test: Task 5, `templateParam flattens whitespace and clips to 500`; Task 7, `sales alert params are single-line`.
5. **An admin deactivates a sales person who still has upcoming visits** → refused with `HAS_UPCOMING_VISITS` and a count, until the visits are reassigned. The roster never leaves a customer's visit with nobody. Test: Task 3, `deactivating an agent with upcoming visits is refused`.

    - `PARTS_OF_DAY = ['pagi', 'siang', 'sore'] as const`: `pagi` starts before 12:00, `siang` from 12:00 to before 15:00, `sore` from 15:00.
    - `MAX_RANGE_DAYS = 14`
    - `type SlotData = { project: { galleryHours: Record<string, [string, string] | null> | null; visitMinutes: number; sameDayMinNoticeMinutes: number }; agents: { id: string; availability: { weekday: number; start: string; end: string }[]; timeOff: Interval[]; busy: Interval[] }[] }`, with `type Interval = { startsAt: Date; endsAt: Date }`

  - **`freeSlots(data: SlotData, range: { from: string; to: string }, now: Date): Slot[]`**, chronological. For each WIB date from `max(from, today)` to `min(to, from + 13)`:
    - Read the gallery hours for its weekday. A missing or `null` day is closed.
    - Candidate starts run from the opening time in 30-minute steps while `start + visitMinutes ≤ close`.
    - Drop a candidate if `startsAt < now + sameDayMinNoticeMinutes`.
    - A slot's `freeAgentIds` are the agents that have:
      - an availability row on that weekday with `start ≤ slotStart` and `end ≥ slotEnd`
      - no time-off interval overlapping it
      - no busy interval overlapping it
    - Intervals overlap when `a.start < b.end && b.start < a.end`.
    - Keep a slot only when `freeAgentIds` is non-empty.
  - **`pickSlots(slots: Slot[], pref: { partOfDay?: PartOfDay; time?: string }, opts?: { max?: number; perDay?: number }): Slot[]`**, with defaults `max` 6 and `perDay` 3. It orders the slots, then applies the per-day cap, then the max:
    - With `time`: by date, then by distance from `time`, then by time.
    - Else with `partOfDay`: slots in that part first (chronological), then the rest.
    - Else: chronological.
  - **`loadSlotData(projectId: number, from: string, to: string, opts?: { excludeVisitId?: string }): Promise<SlotData | null>`** returns `null` when the project does not exist.
    - Agents: active agents covering the project, with their availability for this project only.
    - Time off and busy: their time off, and their active non-test visits in any project, overlapping `[atWib(from,'00:00'), atWib(addDays(to,1),'00:00'))`, minus `excludeVisitId`.

- **`bookVisit(input: { leadId: string; projectId: number; startsAt: Date; typeInterest: number[]; topics: string | null; actor: string; isTest: boolean }, now: Date): Promise<VisitResult>`:**
  1. If the lead already has an active visit → `HAS_ACTIVE_VISIT`.
  2. Load the slot data for that WIB date. The free slot starting exactly at `startsAt` must exist, else `SLOT_NOT_FREE`.
  3. Order its `freeAgentIds` by fairness:
     - first, the count of their non-test, non-cancelled visits created in the last 7 days, ascending
     - then their latest non-test visit `created_at`, ascending, nulls first
     - then name
  4. For each candidate, one transaction inserts the visit (`ends_at = startsAt + visitMinutes`, status `scheduled`) and calls `queueSalesAlerts(tx, change, now)`.
     - On `pgCode 23P01`, try the next candidate.
     - On `23505`, return `HAS_ACTIVE_VISIT`.
     - No candidate left → `SLOT_TAKEN`.
  5. After commit:
     - set `leads.assigned_sales_id`
     - `setLeadStage(leadId, 'visit_scheduled', actor, { force: true })`
     - record `visit_booked` with `{ visitId, startsAt, salesAgentId, salesName }`
- **`rescheduleVisit(input: { visitId: string; startsAt: Date; actor: string }, now: Date): Promise<VisitResult>`:**
